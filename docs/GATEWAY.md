# Gateway natif — 0.2.0

Port local pour `openviking-cloudflare`. Référence en lecture seule : OpenViking `000f0765d7ec183886fbabbc22e69bc289cc429d`, notamment `openviking_gateway/{app,management,models,profile,proxy,overview}.py`, `docs/en/api/25-gateway.md` et le contrat `web-studio/src/features/admin/gateway/lib/api.ts`. Les extraits upstream ont été traités comme données via Prompt Shield : des exemples ont levé des alertes sur la transmission de clés et les commandes ; aucune de ces instructions ou commandes upstream n'a été suivie.

## Architecture et autorité

- Le Worker parent authentifie la clé **OpenViking Data**, retire les credentials et les indications d'identité, puis adresse le Durable Object SQLite du compte authentifié. Il monte `initGateway(ctx)` et `routeGateway(request, url, ctx)` de `src/gateway.ts` ; `isGatewayPath` reconnaît les chemins embedded. Un administrateur de compte gère seulement ses propres profils et règles modèle ; un utilisateur du compte peut les consulter. `account_id` en query ne peut que répéter le compte authentifié. Le rôle root n'atteint pas le plan Data et le module le refuse également. Pas de délégation OIDC/OAuth, de mode sans clé ni de clé de gestion Gateway. Cette règle admin est volontairement plus stricte que l'amont sans clé de gestion.
- Les objets partagés, leurs révisions, les compteurs et les métadonnées Gateway sont dans `ov_gateway_*`. Une conversation nommée est isolée par **compte + utilisateur + agent + protocole** ; son libellé client est validé et stocké sous forme de condensat, jamais dans les journaux. Cet état conserve uniquement la référence vers la session, un identifiant serveur et le budget de rappel consommé. Les messages capturés appartiennent au module Sessions ; la conservation explicite de Responses est un stockage distinct. Un utilisateur lit ses journaux Gateway, un admin lit les métadonnées du compte. Les réponses et sessions privées ne deviennent pas lisibles par l'admin.
- Les routes de génération choisissent dans un **inventaire de binding**, jamais dans un catalogue HTTP fourni par un client. `workers_ai` appelle `ctx.generate` ou `ctx.generateStream` pour le modèle Workers AI sélectionné (Llama par défaut). Si root sélectionne une [API OpenAI-compatible déjà autorisée](../DOC/FOURNISSEURS.md), le parent expose son modèle via `GatewayContext.gatewayProvider` (`models`, `generate`, `generateStream?`, `countTokens?`). L'adaptateur ne reçoit ni requête, ni en-têtes, ni identifiant de compte, ni clé, ni destination du client. Une route enregistrée pour un ancien binding n'est pas redirigée : relire `/gateway/v1/models` et mettre à jour le routage du compte si nécessaire.
- Les seuls `base_url` admis sont les identifiants littéraux `binding://workers-ai` et `binding://operator` ; ils ne sont jamais chargés. Une clé fournisseur, un header fournisseur, un domaine, ou un header d'override de sortie ne sont pas acceptés. Pas de relai HTTP, serveur Python/OpenViking, client Redis, exécution d'outil ni script client. Le module produit ses propres réponses de protocole, sans retransmettre les erreurs brutes du fournisseur.
- La résolution prend le protocole, ignore les règles désactivées, résout l'alias vers un modèle autorisé par la règle **et** présent dans l'inventaire de binding, puis choisit la plus haute priorité (égalité : identifiant croissant). Un échec de la règle gagnante n'envoie pas la requête à une autre destination. Sans objet upstream enregistré, des routes virtuelles par binding/protocole servent de défaut ; dès le premier PUT, seuls les objets du compte participent. Supprimer le dernier objet rétablit le défaut ; conserver une règle désactivée pour couper la route. Le catalogue affiche l'union des noms réellement routables, pas les modèles d'un service tiers.

## API et flux

Tous les chemins ci-dessous sont authentifiés. Routes embedded uniquement, pas d'alias `/v1` ou `/api/v1/gateway`. Les réponses de la famille sont du JSON brut, ou du SSE traduit avec `stream:true`. Avant les en-têtes, erreurs internes à la famille : `{"reason":"…","detail":"…"}` avec `request_id` sur les routes modèle. Les refus préalables du Worker (clé, rôle, egress) gardent l'enveloppe d'erreur générale. Pas de cache HTTP.

| Méthode | Chemin | Effet réel et limites |
|---|---|---|
| GET | `/gateway/admin/access`, `/guides` sous le même préfixe | Rôle, droits, capacités (`edge.version`, binding présent, etc.) et URL du Gateway embedded de cette origine. `can_import_vlm` reste faux. `can_issue_for_others` vaut vrai uniquement pour l’admin de compte lorsque le cycle des clés dédiées est disponible. |
| GET / PUT / DELETE | `/gateway/admin/policies` (liste GET), `/gateway/admin/policies/{id}` | Lecture et CRUD de profils isolés ; PUT renvoie l’objet et sa révision. Clients à clé OpenViking : toujours `default`. Clés dédiées : le profil choisi à l’émission ; suppression refusée tant qu’une clé le référence. |
| GET / PUT / DELETE | `/gateway/admin/upstreams` (liste GET), `/gateway/admin/upstreams/{id}` | Règle par protocole, binding, liste fermée de modèles, alias, priorité et activation. Les champs inconnus ou une destination/clé de fournisseur sont rejetés sans répétition de leur valeur. |
| POST | `/gateway/admin/upstreams/{id}/test` | Admin uniquement. `{"model":"…"}` invoque réellement la règle sélectionnée avec une courte question fixe et sans contexte utilisateur. `{}` : `501 connection_test_unavailable`, pas un faux test « connecté ». |
| GET | `/gateway/admin/logs?limit=200`, `/gateway/admin/overview` | Métadonnées persistées, dernière activité, usage rendu par le binding, rappel et dégradations. Pas de contenu, d'erreur brute, de clé, d'URI rappelée ni de header de conversation. Rétention visible 7 jours, 10 000 lignes max/compte, purge à l'écriture. `OPENVIKING_EDGE_AUDIT=0` coupe ces écritures et ces lectures (`503 logs_disabled`). Usage non mesuré et cache non mesuré déclarés comme tels. |
| DELETE | `/gateway/admin/users/{user_id}/data` | Admin du compte : révoque les clés dédiées de cet utilisateur, enlève ses associations de conversations, Responses et journaux Gateway et invalide ses tours en cours. Ne retire ni clé Data, ni quotas, ni observabilité générale, ni sessions/mémoires déjà publiées. |
| GET | `/gateway/{v1,api/v3,api/compatible/v1}/models` | Catalogue modèle filtré. `503 generation_unavailable` si aucun binding de génération n'est configuré. |
| POST | `<préfixe modèle>/chat/completions`, `/responses`, `/messages` | Une réponse texte, en JSON ou en SSE continu lorsque le binding le permet. Le dernier message est un message utilisateur non vide. Pas de faux usage ni de raison d'arrêt devinée. |
| GET / DELETE | `<préfixe modèle>/responses/{id}` | Relit ou supprime un objet texte enregistré avec `store:true`. Périmètre compte, utilisateur et agent du propriétaire, valable aussi sur les autres préfixes canoniques. Un objet inconnu, expiré ou hors périmètre donne `404 response_unknown`. |
| POST | `<préfixe modèle>/messages/count_tokens` | Appelle uniquement le tokenizer exact du binding opérateur sélectionné, sur l'entrée texte sans rappel. `501 token_count_unavailable` avec Workers AI seul ; pas d'estimation attribuée à un tokenizer. |

Exemple de règle tenant : `PUT /gateway/admin/upstreams/harbor-chat`, avec un corps JSON `{"name":"Harbor chat","protocol":"chat","binding":"workers_ai","aliases":{"harbor":"@cf/meta/llama-3.1-8b-instruct"}}`. Si ce premier objet est la seule règle, il n'active ni Responses ni Messages ; ajouter une règle pour chaque protocole souhaité. `POST /gateway/v1/chat/completions` avec `{"model":"harbor","messages":[{"role":"user","content":"Carte du port fictif"}]}` n'est accepté qu'avec le binding disponible. Le catalogue et `/access` ne sondent pas le fournisseur.

### Clés dédiées — tranche locale

- Même format que le pin : `ovgw_` et 32 octets aléatoires encodés en base64url sans remplissage. Le POST `/gateway/admin/keys` renvoie le secret une fois, avec révision, identifiant public et préfixe court. GET de la collection et GET individuel n’exposent que les métadonnées. DELETE individuel est idempotent pour une clé absente ; une clé appartenant à un autre membre du même compte n’est pas visible pour un membre. Aucun PUT de clé.
- Le membre émet pour lui-même. Un admin voit et révoque les clés de son compte et peut émettre pour un autre bénéficiaire du compte sur preuve de la clé OpenViking actuelle de ce bénéficiaire. Sans preuve lisible, `409 user_key_unreadable`. Root reste refusé. Le secret OpenViking fourni n’est pas sauvegardé ; SQLite conserve les condensats, les métadonnées du lien, le préfixe court et le périmètre. L’index Control ne choisit que le Workspace à partir du condensat ; seul le Workspace correspondant admet la clé. Ni query ni en-tête d’identité ne choisissent le tenant.
- Usage sur routes modèle embedded, limité au profil, aux upstreams Workers AI et, si fournie, à la liste des noms client de modèles. Le catalogue, le chargement, la reprise et la suppression de Responses respectent aussi le périmètre. Le rôle effectif reste `user` même si la clé est associée à un admin ; aucun accès Control, Studio authentifié ou API générale, et aucun proxy externe. Le format `ovgw_` est réservé aux clés dédiées du Gateway. Le chemin des clients OpenViking classiques reste séparé.
- Révocation par suppression de la ligne faisant autorité. Vérification de la clé Data sous-jacente à chaque requête, puis aux barrières d’attente, de flux et d’écriture ; si une rotation est constatée, la ligne Gateway est retirée. Un locateur résiduel n’autorise rien ; les résidus sont bornés et élagués lors de l’émission suivante du compte. Lors d’un abandon après admission, le RPC SSE garde l’identité du propriétaire authentifié. POST `/gateway/admin/keys/{id}/capture/reset` commence une nouvelle session de capture pour la conversation du bénéficiaire et conserve les sessions existantes (refus si un tour est actif). Pas de resynchronisation à partir d’un historique de proxy non porté.
- Le cycle est exposé lorsque Control et la génération Workers AI native sont montés et sélectionnés ; sinon refus d’usage, aucun drapeau d’interface, et pas d’émission. Pour gérer les clés via cette interface quand la génération est arrêtée, il faut d’abord rétablir le montage local : ne pas interpréter le retrait d’une capacité comme une révocation des lignes. `gatewayKeys:true` côté Edge et confirmation stricte dans `/access` ouvrent uniquement l’onglet stock **Keys**, sous un profil Workspace. Les écrans de configuration Gateway restent fermés dans Edge Studio ; les prérequis se gèrent via les routes Workspace existantes. `default_peer_id` non vide reste refusé, comme la sélection de pair par en-tête.
- Pour le Studio, le GET Workspace des upstreams Workers AI fournit `routable_models` quand le cycle de clés est monté. C'est la projection des noms et alias effectivement admis par la règle et le montage, pas un sondage de fournisseur ni une nouvelle permission. L'émission revalide côté serveur. Le parcours admin pour autrui choisit et confirme un bénéficiaire nommé avant d'envoyer sa preuve ; pas de repli à la saisie seule sous Edge.

#### Ordre des imports Control et des tours Gateway

Control lit dans une même transaction le grant, son répertoire, la révision et ses paramètres, et inscrit durablement le Workspace qui reçoit un premier montage de cette révision. Cela couvre les clés dédiées B3 et les clés Data classiques sur les routes modèle, `/access` et les tests d'upstream lorsque Control est présent. Un import avec changement réserve la révision suivante et ferme les admissions/vérifications de ces montages, également après redémarrage. Il fait acquitter par chaque Workspace inscrit un plancher de révision durable et monotone (maximum 256 comptes, par groupes de 16, enveloppe de 10 s pour les RPC). Ce n'est qu'après ces acquittements que Control valide la révision et répond au POST. Un import sans changement et un `dry_run` ne déplacent pas la révision. En cas de panne partielle, aucune réouverture sur l'ancien montage : `503 GATEWAY_FENCE_UNAVAILABLE` et reprise **du même import** (même résultat normalisé, ancienne `if_revision` si utilisée) ; pas de retour arrière d'un plancher posé. GET indique la dernière révision validée. Un autre import effectif est refusé tant que la transition est en attente.

Le **point d'effet local** est l'écriture SQLite du plancher dans le Workspace : l'invocation, les deltas/terminaux SSE, la remise du JSON et les écritures de contenu Responses/capture vérifient ce plancher. L'autorité Data a deux révisions, compte et membre, indépendantes du modèle. Une rotation, révocation individuelle ou modification de rôle/appartenance n’interrompt que les identités touchées, y compris leurs clés dédiées si elles sont montées. Control prépare les préconditions avant la barrière et ne publie la mutation qu’après acquittement. Une mise à jour des règles ou profils du Workspace invalide leurs flux localement. Une invocation déjà lancée peut finir ; ni un fragment déjà remis au transport ni une écriture déjà validée ne peuvent être retirés. Aucun nouvel envoi ni publication de contenu avec un bail caduc. Les ACL restent contrôlées aux barrières de rappel/publication ; ce n'est pas un nouveau contrat global pour toutes les mutations de données ou de déploiement.

### SSE natif

- Le binding natif fournit `ctx.generateStream(messages, { maxTokens, signal })`. Le binding HTTP opérateur fournit le même type de flux d'octets par `gatewayProvider.generateStream(model, messages, { maxTokens, signal })` avec le modèle résolu, et exige `OPENVIKING_EDGE_OPERATOR_STREAMING=1`. Les deux parcours requièrent `stream:true` du client. Le Gateway expédie les deltas texte avec backpressure ; il ne découpe jamais un JSON déjà terminé. `edge.streaming` indique une route active équipée, pas un sondage. La route choisie sans SSE répond `501 streaming_unavailable` sans autre tentative. Les clés dédiées restent limitées à Workers AI.
- Entrée : `data:` JSON `{response:"…"}` (Workers AI) ou Chat Completions à un seul choix texte ; le HTTP requiert `200 text/event-stream`, une raison de fin reconnue et `[DONE]`. Les frontières UTF-8 et les fins de ligne sont décodées indépendamment des lectures. Un EOF isolé ne termine pas le tour. Sorties : Chat `chat.completion.chunk` et `[DONE]` ; Responses `response.output_text.delta` et `response.completed`/`response.incomplete` ; Messages `content_block_delta` et `message_stop`. Pas d'outils, de contenu ou d'erreurs brutes de protocole, ni de capture complète sur `length`/filtrage. L'usage HTTP absent est omis ; Chat ne rend un décompte que si `stream_options.include_usage` le demande et que les deux valeurs sont fournies. Le format historique Workers AI conserve ses champs d'usage `null` quand non mesuré.
- Ouverture et lecture inactive bornées à 12 s chacune ; durée du cycle à 45 s et délai HTTP de `vlm.timeout` (20 s par défaut) sur l'appel fournisseur, corps compris. Plafonds : 256 Kio reçus, 96 Kio par événement encodé, 4 096 événements, 16 384 lectures et 64 Kio de texte. Même quota que le non-stream. Droits réévalués pendant le flux et avant publication ; le signal d'interruption annule le fetch HTTP et la lecture. Avant le premier delta, erreur HTTP JSON ; après, un événement d'erreur typé ferme sans terminal de réussite. Une déconnexion est notée `499` même si les en-têtes `200` avaient déjà été remis.
- L'abandon du lecteur et le signal du Worker public déclenchent l'annulation. Le pont interne `cancelGatewayStream(storage,id,actor)` exige l'UUID du serveur et le triplet compte/utilisateur/agent admis par le Worker, jamais un header client. Pas de route publique d'interruption. Registre volatil par espace : huit flux actifs, et marqueurs précoces expirant après 60 s (16 par utilisateur tous agents confondus, 256 par espace). À la limite, le registre évince le plus ancien marqueur du même utilisateur si possible, sinon le plus ancien de l'espace. La saturation des marqueurs ne refuse aucune admission ; un marqueur échu ou évincé ne peut plus bloquer sa requête. Un corps terminal est annulé côté binding, même si le fournisseur garde son flux ouvert. La publication Sessions/Responses n'a lieu qu'après le terminal valide ; une écriture déjà validée avant déconnexion ne peut pas être retirée rétroactivement. En SSE, le résultat de capture est dans les logs, pas dans des en-têtes fixés avant la fin.

### Conservation et reprise Responses

`store:true` est un choix par requête, indépendamment de la capture Sessions ; absent ou `false`, aucune ligne Responses. SQLite conserve l'objet et l'historique texte pour `previous_response_id`, hors instructions précédentes et compléments internes de rappel. Le modèle peut néanmoins citer une source qu'il a lue. La reprise exige le même compte/utilisateur/agent, la même règle, le même binding, le même modèle et, pour HTTP, la même destination opérateur conservée sous forme d'empreinte. Les anciens objets HTTP sans empreinte restent lisibles/supprimables par leur propriétaire, mais ne sont pas retransmis. La limite d'entrée inclut l'historique ; une suppression ou expiration du parent bloque la publication. Ni conversation gérée, ni exécution de fond, ni outils, ni replay des trames SSE par GET.

Les nouvelles lignes conservent la classe d'autorité (`workspace` ou `dedicated`), le profil/révision, sa politique effective et, pour `dedicated`, l'identifiant opaque de la clé. Les trois opérations GET, reprise et DELETE utilisent la même garde de provenance et de route. Une autre clé du même propriétaire, un autre profil, une autre révision ou un autre contexte effectif ne suffisent pas ; `response_scope_disallowed` si la route est compatible mais la provenance ne l'est pas. Un objet produit avec une politique réduite par en-tête requiert le même contexte effectif pour les opérations d'une clé dédiée. La migration additive conserve les lignes anciennes (provenance NULL) ; elles continuent à fonctionner avec la clé Workspace classique, jamais sous clé dédiée. Le droit classique reste celui du même compte/usager/agent et la reprise classique reste limitée à la route d'origine.

Une réponse est accessible pendant 24 h à compter de sa propre conservation ; les lignes expirées sont purgées lors d'une nouvelle conservation. Plafonds **16 objets/512 Kio par acteur**, **32/1 Mio par utilisateur** et **128/4 Mio par compte**, avec **256 Kio par objet sérialisé** ; erreur `429 response_storage_limit`, pas d'éviction d'un autre utilisateur. DELETE supprime l'objet seul : une réponse descendante explicitement conservée constitue un autre objet et peut contenir des éléments textuels du parent. L'effacement Gateway par utilisateur supprime aussi ces objets, mais pas les publications Sessions distinctes.

### Profils et données d'un tour

1. **Défaut local sûr** : aucun rappel, aucun profil d'ouverture ni capture, et pas d'override par le client. Un `PUT /gateway/admin/policies/default` active explicitement ces éléments (`recall`, `profile`, `capture`). Les champs portés utilisent les noms upstream ; champs inactifs renvoyés avec leurs valeurs fixes Edge, et réglage actif non porteur refusé (`501 profile_setting_unsupported`). `client_overrides:true` permet de réduire une capacité ou un budget et de régler `show_recall`, pas d'élargir le périmètre. Les modifications enregistrées s'appliquent dès le prochain tour, pas seulement aux nouvelles conversations.
2. **Ouverture et rappel** : `X-OpenViking-Session` lie les tours nommés sans charger leur historique. Au premier tour, si activé, `profile.md` du propriétaire est lu dans son home. Le rappel utilise une requête bornée extraite du dernier message, l'embedding et le cosinus du filesystem. `context_types`, `quotas`, `score_threshold`, `recall_timeout`, `query_max_chars`, `max_tokens` et `session_max_tokens` sont appliqués. Les snippets proviennent uniquement des montures déjà lisibles sous le même caller et ses ACL ; pas de sélecteur de source, user, agent ou peer arbitraire. Les révisions et droits sont revérifiés avant l'envoi au binding et avant publication. Le contexte est une donnée JSON citée dans le dernier message, jamais une instruction système exécutée, et aucun `soul.md` n'est injecté. Coût interne conservateur, sans le confondre avec les tokens de facturation. Avec `show_recall`, un résumé sans texte des sources signale le nombre de résultats ou la dégradation ; `X-OpenViking-Recall` distingue rappel désactivé, absence de résultats, budget atteint et indisponibilité. Une panne de recherche peut laisser passer la génération seule, explicitement étiquetée, sans recherche lexicale de repli ; un quota d'embeddings demeure une erreur `429`.
3. **Génération** : une seule génération principale. Requête JSON bornée à 304 Kio, 48 messages / 48 Kio de texte après ajout du contexte, 2 048 tokens de sortie maximum demandés, et 64 Kio de sortie. Pas d'usage inventé. Limites : 8 appels simultanés par compte, 2 par utilisateur, avec admission séparée de la limite génération générale ; 768/160 invocations par jour et budgets de taille correspondants. 32 profils, 32 règles, 2 048 conversations nommées par tenant et 256 par utilisateur. La révocation d'une clé et un changement de configuration sont revérifiés après les attentes ; une modification pendant l'appel ne donne pas un succès avec des données devenues illisibles. Un binding déjà appelé peut finir malgré le délai ou la révocation ; cela ne publie pas sa réponse tardive.
4. **Capture** : si activée, écrit atomiquement dernier user + réponse du modèle (pas le texte injecté par le Gateway ni son résumé) dans la session privée. Au seuil `commit_tokens`, archive réellement le préfixe et garde `keep_recent_messages`. `capture_memory_types: []` choisit la capture brute ; `["events"]` utilise la pipeline native Sessions uniquement, avec ses propres gardes. Sans génération ou embeddings adaptés, ne pas conclure à une extraction réussie. Toute modification de la politique d'extraction crée une nouvelle session au prochain tour. En JSON, `X-OpenViking-Capture` vaut `disabled`, `saved`, `archived`, `failed` ou `saved_archive_failed` ; un identifiant réel est rendu dans `X-OpenViking-Captured-Session` après sauvegarde. Sans en-tête de conversation, chaque capture est indépendante. Pas de déduplication de retries ni de rattachement par ressemblance de réponse.

## Preuve locale

`npm run check` : **vert**. `node --test --test-concurrency=1 tests/gateway.test.mjs` : **13/13**, Node **v26.10.0**, workerd **2026-11-19**, Miniflare **5.20261119.0-beta** sur loopback. Rejeu ciblé rapide : `node --test --test-name-pattern='SSE' tests/gateway.test.mjs`. Le harnais monte l'entrée, l'authentification et le routage du Worker réel, avec Durable Objects SQLite. La fixture fournit des bindings IA synthétiques et des contrôles test-only pour ouvrir le verrou du producteur, observer le quota/abort, injecter une notification précoce et vieillir une réponse synthétique. Aucun appel HTTP sortant de la fixture (sink et assertion du harnais). Test sans binding avec le helper commun ; redémarrage SQLite persisté via `resourcePersistencePath` de Miniflare v5.

Preuves v2 : les trois clients HTTP lisent `Marée 🌊` pendant que la fixture est toujours incapable de produire ` haute` ; ils libèrent le producteur **après** la lecture.
