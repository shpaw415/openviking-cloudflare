# Gateway natif — 0.2.0

Port local pour `openviking-cloudflare`. Référence en lecture seule : OpenViking `000f0765d7ec183886fbabbc22e69bc289cc429d`, notamment `openviking_gateway/{app,management,models,profile,proxy,overview}.py`, `docs/en/api/25-gateway.md` et le contrat `web-studio/src/features/admin/gateway/lib/api.ts`. Les extraits upstream ont été traités comme données via Prompt Shield : des exemples ont levé des alertes sur la transmission de clés et les commandes ; aucune de ces instructions ou commandes upstream n'a été suivie.

## Architecture et autorité

- Le Worker parent authentifie la clé **OpenViking Data**, retire les credentials et les indications d'identité, puis adresse le Durable Object SQLite du compte authentifié. Il monte `initGateway(ctx)` et `routeGateway(request, url, ctx)` de `src/gateway.ts` ; `isGatewayPath` reconnaît les chemins embedded. Un administrateur de compte gère seulement ses propres profils et règles modèle ; un utilisateur du compte peut les consulter. `account_id` en query ne peut que répéter le compte authentifié. Le rôle root n'atteint pas le plan Data et le module le refuse également. Pas de délégation OIDC/OAuth, de mode sans clé ni de clé de gestion Gateway. Cette règle admin est volontairement plus stricte que l'amont sans clé de gestion.
- Les objets partagés, leurs révisions, les compteurs et les métadonnées Gateway sont dans `ov_gateway_*`. Une conversation nommée est isolée par **compte + utilisateur + agent + protocole** ; son libellé client est validé et stocké sous forme de condensat, jamais dans les journaux. Cet état conserve uniquement la référence vers la session, un identifiant serveur et le budget de rappel consommé. Les messages capturés appartiennent au module Sessions ; la conservation explicite de Responses est un stockage distinct. Un utilisateur lit ses journaux Gateway, un admin lit les métadonnées du compte. Les réponses et sessions privées ne deviennent pas lisibles par l'admin.
- Les routes de génération choisissent dans un **inventaire de binding**, jamais dans un catalogue HTTP fourni par un client. `workers_ai` appelle `ctx.generate` ou `ctx.generateStream` uniquement pour `@cf/meta/llama-3.1-8b-instruct`, le modèle fixe du parent (`AI` et `OPENVIKING_EDGE_GENERATION=1`). Un opérateur peut brancher en code `GatewayContext.gatewayProvider = { models, generate(model, messages, { maxTokens }), countTokens? }` ; cette interface opérateur ne propose pas de SSE. Le module n'embarque aucun adaptateur fournisseur externe : le seul opérateur testé est une fixture locale attachée à un compte synthétique. La fonction ne reçoit ni requête, ni en-têtes, ni identifiant de compte, ni clé, ni destination client. Une future liaison doit rester de confiance, avec un inventaire et un périmètre déclarés côté opérateur.
- Les seuls `base_url` admis sont les identifiants littéraux `binding://workers-ai` et `binding://operator` ; ils ne sont jamais chargés. Une clé fournisseur, un header fournisseur, un domaine, ou un header d'override de sortie ne sont pas acceptés. Pas de relai HTTP, serveur Python/OpenViking, client Redis, exécution d'outil ni script client. Le module produit ses propres réponses de protocole, sans retransmettre les erreurs brutes du fournisseur.
- La résolution prend le protocole, ignore les règles désactivées, résout l'alias vers un modèle autorisé par la règle **et** présent dans l'inventaire de binding, puis choisit la plus haute priorité (égalité : identifiant croissant). Un échec de la règle gagnante n'envoie pas la requête à une autre destination. Sans objet upstream enregistré, des routes virtuelles par binding/protocole servent de défaut ; dès le premier PUT, seuls les objets du compte participent. Supprimer le dernier objet rétablit le défaut ; conserver une règle désactivée pour couper la route. Le catalogue affiche l'union des noms réellement routables, pas les modèles d'un service tiers.

## API et flux

Tous les chemins ci-dessous sont authentifiés. Routes embedded uniquement, pas d'alias `/v1` ou `/api/v1/gateway`. Les réponses de la famille sont du JSON brut, ou du SSE traduit avec `stream:true`. Avant les en-têtes, erreurs internes à la famille : `{"reason":"…","detail":"…"}` avec `request_id` sur les routes modèle. Les refus préalables du Worker (clé, rôle, egress) gardent l'enveloppe d'erreur générale. Pas de cache HTTP.

| Méthode | Chemin | Effet réel et limites |
|---|---|---|
| GET | `/gateway/admin/access`, `/guides` sous le même préfixe | Rôle, droits, capacités (`edge.version`, binding présent, etc.) et URL du Gateway embedded de cette origine. `can_import_vlm` et `can_issue_for_others` sont faux. |
| GET / PUT / DELETE | `/gateway/admin/policies` (liste GET), `/gateway/admin/policies/{id}` | Lecture et CRUD de profils isolés; PUT remplace et renvoie ses champs avec `id` et `revision`. Sans clé `ovgw_`, seul `default` est utilisé par les requêtes modèle ; les profils nommés sont des objets réutilisables, pas des sélecteurs clients. |
| GET / PUT / DELETE | `/gateway/admin/upstreams` (liste GET), `/gateway/admin/upstreams/{id}` | Règle par protocole, binding, liste fermée de modèles, alias, priorité et activation. Les champs inconnus ou une destination/clé de fournisseur sont rejetés sans répétition de leur valeur. |
| POST | `/gateway/admin/upstreams/{id}/test` | Admin uniquement. `{"model":"…"}` invoque réellement la règle sélectionnée avec une courte question fixe et sans contexte utilisateur. `{}` : `501 connection_test_unavailable`, pas un faux test « connecté ». |
| GET | `/gateway/admin/logs?limit=200`, `/gateway/admin/overview` | Métadonnées persistées, dernière activité, usage rendu par le binding, rappel et dégradations. Pas de contenu, d'erreur brute, de clé, d'URI rappelée ni de header de conversation. Rétention visible 7 jours, 10 000 lignes max/compte, purge à l'écriture. `OPENVIKING_EDGE_AUDIT=0` coupe ces écritures et ces lectures (`503 logs_disabled`). Usage non mesuré et cache non mesuré déclarés comme tels. |
| DELETE | `/gateway/admin/users/{user_id}/data` | Admin du compte : enlève les associations de conversations, Responses conservées et journaux Gateway de l'utilisateur et invalide les tours en cours. Ne retire ni clé Data, ni quotas, ni observabilité générale, ni sessions/mémoires déjà publiées. |
| GET | `/gateway/{v1,api/v3,api/compatible/v1}/models` | Catalogue modèle filtré. `503 generation_unavailable` si aucun binding de génération n'est configuré. |
| POST | `<préfixe modèle>/chat/completions`, `/responses`, `/messages` | Une réponse texte, en JSON ou en SSE continu lorsque le binding le permet. Le dernier message est un message utilisateur non vide. Pas de faux usage ni de raison d'arrêt devinée. |
| GET / DELETE | `<préfixe modèle>/responses/{id}` | Relit ou supprime un objet texte enregistré avec `store:true`. Périmètre compte, utilisateur et agent du propriétaire, valable aussi sur les autres préfixes canoniques. Un objet inconnu, expiré ou hors périmètre donne `404 response_unknown`. |
| POST | `<préfixe modèle>/messages/count_tokens` | Appelle uniquement le tokenizer exact du binding opérateur sélectionné, sur l'entrée texte sans rappel. `501 token_count_unavailable` avec Workers AI seul ; pas d'estimation attribuée à un tokenizer. |

Exemple de règle tenant : `PUT /gateway/admin/upstreams/harbor-chat`, avec un corps JSON `{"name":"Harbor chat","protocol":"chat","binding":"workers_ai","aliases":{"harbor":"@cf/meta/llama-3.1-8b-instruct"}}`. Si ce premier objet est la seule règle, il n'active ni Responses ni Messages ; ajouter une règle pour chaque protocole souhaité. `POST /gateway/v1/chat/completions` avec `{"model":"harbor","messages":[{"role":"user","content":"Carte du port fictif"}]}` n'est accepté qu'avec le binding disponible. Le catalogue et `/access` ne sondent pas le fournisseur.

### SSE natif

- Contrat parent : `ctx.generateStream(messages, { maxTokens, signal }) → Promise<ReadableStream<Uint8Array>>`. L'opt-in est celui de la génération Workers AI ; une requête demande en plus `stream:true`. Le Gateway reçoit les octets SSE bruts. Il lit et expédie les deltas texte au fur et à mesure, avec backpressure ; le texte accumulé sert uniquement aux événements finaux Responses et aux écritures autorisées. Il ne convertit jamais une génération JSON finie en faux stream. `edge.streaming` indique la présence d'une route active sur ce binding, pas un sondage de production. La route choisie sans stream répond `501 streaming_unavailable`, sans retomber sur un autre binding ni appeler la version non-streaming.
- Entrée : `data:` JSON `{response:"…"}` ou chunk Chat à un seul choix texte, UTF-8 et fins de ligne décodées même si elles chevauchent deux fragments, commentaires ignorés, terminal `[DONE]` explicite. Un EOF isolé n'est pas un terminal. Les événements fournisseur non reconnus, erreurs et dépassements ne sont pas relayés bruts. Sorties : `chat.completion.chunk` et `[DONE]` ; événements Responses `response.created`/`in_progress`, item, part, deltas, fin ordonnée et `response.completed` ou `response.incomplete` ; événements Messages `message_start`, `content_block_*`, `message_delta`, `message_stop`. Un arrêt `length` ou filtrage déclaré ne devient pas une capture complète. `stream_options.include_usage` (Chat) n'ajoute une mesure finale que si le binding a rendu les deux valeurs ; l'usage inconnu reste manquant ou `null`.
- Ouverture et lecture inactive bornées à 12 s chacune ; durée du cycle de streaming à 45 s. Plafonds : 256 Kio reçus, 96 Kio par événement encodé, 4 096 événements, 16 384 lectures et 64 Kio de texte généré. Charge imputée au même quota que le non-streaming. L'admission reste tenue jusqu'à la fin du corps, les droits sont réévalués périodiquement et avant publication, les révisions vérifiées aux deltas. Avant le premier delta, une faute donne une erreur HTTP JSON ; après, un événement d'erreur typé ferme le flux sans terminal de réussite. `first_chunk_ms`, `stream_error` et une seule écriture de journal identifient le résultat du flux ; une déconnexion est notée `499` même si les en-têtes `200` avaient déjà été remis.
- L'abandon du lecteur et le signal du Worker public déclenchent l'annulation. Le pont interne `cancelGatewayStream(storage,id,actor)` exige l'UUID du serveur et le triplet compte/utilisateur/agent admis par le Worker, jamais un header client. Pas de route publique d'interruption. Registre volatil par espace : huit flux actifs, et marqueurs précoces expirant après 60 s (16 par utilisateur tous agents confondus, 256 par espace). À la limite, le registre évince le plus ancien marqueur du même utilisateur si possible, sinon le plus ancien de l'espace. La saturation des marqueurs ne refuse aucune admission ; un marqueur échu ou évincé ne peut plus bloquer sa requête. Un corps terminal est annulé côté binding, même si le fournisseur garde son flux ouvert. La publication Sessions/Responses n'a lieu qu'après le terminal valide ; une écriture déjà validée avant déconnexion ne peut pas être retirée rétroactivement. En SSE, le résultat de capture est dans les logs, pas dans des en-têtes fixés avant la fin.

### Conservation et reprise Responses

`store:true` est un choix par requête, indépendamment de la capture Sessions ; absent ou `false`, aucune ligne Responses. Pour une réponse terminée, SQLite conserve l'objet remis et l'historique texte reçu/produit qui permet `previous_response_id`, hors instructions précédentes et hors compléments système internes de rappel. Le modèle peut néanmoins citer une source qu'il a déjà lue. La reprise vérifie que l'objet appartient au même compte, utilisateur et agent, et que la règle, le binding et le modèle résolu correspondent ; elle n'envoie pas le contexte à un autre provider. La limite d'entrée inclut l'historique repris ; une suppression ou expiration du parent en cours de requête bloque les publications suivantes. Ni conversation gérée, ni exécution de fond, ni outils, ni historique de streaming rejouable par GET.

Une réponse est accessible pendant 24 h à compter de sa propre conservation ; les lignes expirées sont purgées lors d'une nouvelle conservation. Plafonds **16 objets/512 Kio par acteur**, **32/1 Mio par utilisateur** et **128/4 Mio par compte**, avec **256 Kio par objet sérialisé** ; erreur `429 response_storage_limit`, pas d'éviction d'un autre utilisateur. DELETE supprime l'objet seul : une réponse descendante explicitement conservée constitue un autre objet et peut contenir des éléments textuels du parent. L'effacement Gateway par utilisateur supprime aussi ces objets, mais pas les publications Sessions distinctes.

### Profils et données d'un tour

1. **Défaut local sûr** : aucun rappel, aucun profil d'ouverture ni capture, et pas d'override par le client. Un `PUT /gateway/admin/policies/default` active explicitement ces éléments (`recall`, `profile`, `capture`). Les champs portés utilisent les noms upstream ; champs inactifs renvoyés avec leurs valeurs fixes Edge, et réglage actif non porteur refusé (`501 profile_setting_unsupported`). `client_overrides:true` permet de réduire une capacité ou un budget et de régler `show_recall`, pas d'élargir le périmètre. Les modifications enregistrées s'appliquent dès le prochain tour, pas seulement aux nouvelles conversations.
2. **Ouverture et rappel** : `X-OpenViking-Session` lie les tours nommés sans charger leur historique. Au premier tour, si activé, `profile.md` du propriétaire est lu dans son home. Le rappel utilise une requête bornée extraite du dernier message, l'embedding et le cosinus du filesystem. `context_types`, `quotas`, `score_threshold`, `recall_timeout`, `query_max_chars`, `max_tokens` et `session_max_tokens` sont appliqués. Les snippets proviennent uniquement des montures déjà lisibles sous le même caller et ses ACL ; pas de sélecteur de source, user, agent ou peer arbitraire. Les révisions et droits sont revérifiés avant l'envoi au binding et avant publication. Le contexte est une donnée JSON citée dans le dernier message, jamais une instruction système exécutée, et aucun `soul.md` n'est injecté. Coût interne conservateur, sans le confondre avec les tokens de facturation. Avec `show_recall`, un résumé sans texte des sources signale le nombre de résultats ou la dégradation ; `X-OpenViking-Recall` distingue rappel désactivé, absence de résultats, budget atteint et indisponibilité. Une panne de recherche peut laisser passer la génération seule, explicitement étiquetée, sans recherche lexicale de repli ; un quota d'embeddings demeure une erreur `429`.
3. **Génération** : une seule génération principale. Requête JSON bornée à 304 Kio, 48 messages / 48 Kio de texte après ajout du contexte, 2 048 tokens de sortie maximum demandés, et 64 Kio de sortie. Pas d'usage inventé. Limites : 8 appels simultanés par compte, 2 par utilisateur, avec admission séparée de la limite génération générale ; 768/160 invocations par jour et budgets de taille correspondants. 32 profils, 32 règles, 2 048 conversations nommées par tenant et 256 par utilisateur. La révocation d'une clé et un changement de configuration sont revérifiés après les attentes ; une modification pendant l'appel ne donne pas un succès avec des données devenues illisibles. Un binding déjà appelé peut finir malgré le délai ou la révocation ; cela ne publie pas sa réponse tardive.
4. **Capture** : si activée, écrit atomiquement dernier user + réponse du modèle (pas le texte injecté par le Gateway ni son résumé) dans la session privée. Au seuil `commit_tokens`, archive réellement le préfixe et garde `keep_recent_messages`. `capture_memory_types: []` choisit la capture brute ; `["events"]` utilise la pipeline native Sessions uniquement, avec ses propres gardes. Sans génération ou embeddings adaptés, ne pas conclure à une extraction réussie. Toute modification de la politique d'extraction crée une nouvelle session au prochain tour. En JSON, `X-OpenViking-Capture` vaut `disabled`, `saved`, `archived`, `failed` ou `saved_archive_failed` ; un identifiant réel est rendu dans `X-OpenViking-Captured-Session` après sauvegarde. Sans en-tête de conversation, chaque capture est indépendante. Pas de déduplication de retries ni de rattachement par ressemblance de réponse.

### Écarts encore ouverts

| Famille amont | Statut sur Edge |
|---|---|
| VLM import, auth upstream avec en-têtes/secrets/Coding Plan, URL personnalisées, passthrough générique | Non portés par conception ; configuration par inventaire du binding de confiance. Aucun fournisseur réel n'a été contacté. |
| Clés `ovgw_`, groupe de modèles/profil par clé et capture reset par clé, compte root | `501 gateway_keys_unavailable` pour `/keys`, `/keys/{id}` et `/keys/{id}/capture/reset`. `DELETE /account/data` refusé ; aucun endpoint propriétaire global ajouté. Les lots OIDC, OAuth et gestion des comptes sont distincts. |
| Tools, URLs de transfert signées | `501 tools_unsupported` pour le catalogue et les demandes d'outil ; `501 signed_transfer_unavailable` pour `/gateway/uploads`, `/gateway/downloads`. Les outils ne sont pas exécutés même si un modèle émet du texte qui y ressemble. |
| Protocoles complets des SDK | SSE texte seulement avec Workers AI ; WebSocket : `426`. Pas de média, JSON structuré, paramètres fournisseur libres, batch, cache/reasoning vendor, Responses `input_items` ou background/`cancel`. Les champs hors sous-ensemble sont refusés, pas ignorés. Pas de validation générale des SDK originaux. |
| Conversation longue, peer, mémoire avancée | Pas de compaction, fenêtres pilotées par agent, soul, catalogues d'ouverture, rejeu de rappel, extraction hors events, idle commit/alarmes Gateway, reprise automatique après un échec d'archive, ni auto-inférence de conversation. Entrée trop grande rejetée, pas tronquée silencieusement avant génération. |
| Observabilité et opérations | Sous-ensemble du modèle de logs, pas de cache hits calculés sans données, fichier/Redis/stdout sink, heartbeat, instantanés opérateur ou import de l'ancien stockage. Pas de modification ni preuve navigateur du Gateway Studio ; plusieurs workflows Studio attendent justement clés, VLM ou métriques non portés. |

## Preuve locale

`npm run check` : **vert**. `node --test --test-concurrency=1 tests/gateway.test.mjs` : **13/13**, Node **v26.10.0**, workerd **2026-11-19**, Miniflare **5.20261119.0-beta** sur loopback. La fixture fournit des bindings IA synthétiques et des contrôles test-only pour ouvrir le verrou du producteur, observer le quota/abort, injecter une notification précoce et vieillir une réponse synthétique. Aucun appel HTTP sortant de la fixture (sink et assertion du harnais). Test sans binding avec le helper commun ; redémarrage SQLite persisté via `resourcePersistencePath` de Miniflare v5.

UTF-8 fractionné, EOF nu, erreur émoussée, quota, temps d'attente, changement de profil, pré-annulation avant invocation, vrai RST TCP loopback arrivé au producteur, aucune capture partielle ni faux terminal. Les sept tests v1 sont conservés ; Responses couvre l'opt-in, le redémarrage, l'isolation jusqu'à l'agent, le vrai historique transmis et la suppression/expiration.

Les routes `/api/v1/agent-evolution/experiences/{trajectories,outcomes}` sont déjà montées par VikingBot, hors des chemins Gateway.
