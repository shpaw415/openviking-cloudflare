# OpenViking Edge — fichiers, ACL, index et skills

Référence amont **`000f0765d7ec183886fbabbc22e69bc289cc429d`**, gardée en lecture seule. Ces routes utilisent le SQLite natif du Durable Object, pas un proxy ni le filesystem de l’hôte. Le parent monte `initFilesystem(ctx)` et `routeFilesystem(request, url, ctx)` ; lui seul authentifie et fournit `caller`, `groups`, `aclPrincipals`, `embed` et les hooks optionnels. Ni identité ni appartenance à un groupe ne proviennent du JSON ou d’un en-tête client.

## Espaces et ACL

- `viking://resources/...` est partagé **dans le compte**. ACL directe `inherit` (union avec le parent ; niveau maximal par principal) ou `restricted` (grants directs uniquement). Les descendants héritent de l’ACL effective calculée sur l’arbre SQL courant, pas d’une copie stockée dans l’index. L’admin conserve `manage` implicite. **Différence volontaire avec l’amont ACL activé :** la racine Edge est immuable avec `user:* = read`, pas `manage`. Les ressources alpha sans politique explicite restent donc modifiables uniquement par l’admin. Réinitialiser une ACL revient à hériter, pas à octroyer `manage` au compte.
- `viking://~/` est l’alias de `viking://user/<userId>/`. Ressources, mémoires et skills privés restent isolés par compte/utilisateur, même pour les admins d’un autre utilisateur. `viking://agent` est isolé par compte/utilisateur/agent, sauf `viking://agent/skills`, partagé dans le compte et administré par son admin. Les montes de skills sont protégées contre les modifications génériques. Les namespaces `peers`, `sessions`, `privacy` et `tools` restent gérés séparément.
- `GET`, `PUT`, `DELETE /api/v1/acl` et `POST /api/v1/acl/{grant,revoke}` : `manage` requis. `GET` et mutations renvoient `{uri, acl_mode, direct_entries, inherited_entries, effective_entries}`. `PUT` prend `{uri, acl_mode?, entries?}` ; omettre un champ le préserve, `entries:[]` efface les grants directs, `DELETE` efface et restaure l’héritage. `grant` prend `{uri,principal,level}` et `revoke` `{uri,principal}`. Niveaux `read < write < manage`, principals `user:<id>`, `group:<id>`, `user:*`. Validation par le répertoire du compte ; sans répertoire attesté, seuls le titulaire, ses groupes authentifiés et le wildcard utilisateur peuvent être désignés. Aucun ACL sur une monte privée.
- La lecture directe, les listings, les tags, les résumés, le contenu et les scores sont contrôlés avant usage. Une arborescence ou `grep/glob` ne traverse pas un parent illisible. `find/search` peut découvrir un fichier individuellement partagé sous un parent illisible, comme à l’amont ; le parent n’est alors pas livré dans `searched_directories`. Un résumé exige les droits du répertoire **et** de son sidecar. `read` direct sur un sidecar suit l’ACL de ce chemin. Un état de permissions illisible échoue fermé.
- `write` autorise l’édition, la création dans un parent accessible en écriture et les tags. Pour une copie, `read` est requis sur tout le sous-arbre source. Pour une suppression ou un déplacement, `manage` est requis **sur chaque entrée retirée**. Un écrasement de dossier contrôle aussi tous les descendants de destination qui vont disparaître, même sans correspondant à la source. Le refus d’une seule entrée annule l’opération entière avant mutation. Exception : le remplacement simple d’un fichier par un fichier à la même destination est une mise à jour en place (`write` ; ACL et incarnation de destination conservées). Un nouveau chemin hérite à destination ; les ACL des chemins correspondants sont conservées lors d’un écrasement d’arbre autorisé. Les ACL des URI supprimées ou déplacées ne survivent pas à ces URI. Pas de transfert entre montes.

## API HTTP

Pour les chemins suivants, préfixe `/api/v1`.

| Route | Contrat Edge |
| --- | --- |
| `GET /fs/{ls,tree,stat}` | URI canonique, tri, pagination, tags et résumés facultatifs ; `simple=true` rend une liste d’URI complètes. `extra_fields=count` compte les enfants directs lisibles. |
| `POST /fs/mkdir` ; `POST /fs/{cp,mv}` ; `DELETE /fs` | Parent existant. `mkdir` accepte `description` et `acl`. Copie de dossiers et suppression de sous-arbre sur opt-in récursif. Copie/déplacement sans écrasement par défaut ; `overwrite:true` est atomique et contrôlé à destination. `/resources/{cp,mv}` et `DELETE /resources` sont les variantes limitées aux ressources partagées. |
| `GET /content/{read,download,abstract,overview}` | `read` est un aller-retour UTF-8, avec `offset`/`limit` en lignes ; `raw` ne fait pas de projection mémoire. Téléchargement en pièce jointe `application/octet-stream`, `nosniff`, sans cache ; aucun asset actif sur la même origine. Sur un fichier, les deux routes de résumé préfèrent son niveau dérivé courant ; sans niveau propre, elles conservent la lecture du sidecar du parent. Dans les deux cas les deux chemins sont autorisés. `stat` et `ls` ne remontent pas cette valeur de repli. |
| `POST /content/write` | `replace` crée/remplace sous un parent existant ; `append` exige un fichier. `create` peut créer ses parents manquants dans `resources`, les propres `resources`/`memories` ou la monte `agent` non gérée, et refuse toujours une collision (garde Edge, contrairement à l’alias `replace` amont). ACL, quota et chaîne d’ancêtres revérifiés dans le commit commun ; aucun parent partiel en cas d’erreur. `acl` et tags optionnels. `defer_processing:true` écrit le texte sans vecteur et retire l’ancien index, sans tags/ACL dans la même requête. |
| `POST /content/batch-write` | `root_uri` existant, non virtuel ; opérations uniques dans la même monte et sous la racine. `create`, `replace` et `upsert` matérialisent l’état demandé ; `append` peut créer. Exactement un de `content` et `content_base64` (UTF-8 seulement). `expected_sha256` et `if_absent` sont exclusifs ; `skip_conflicts` rapporte les conflits ordinaires, **jamais** les refus ACL comme conflits ignorables. `created`, `updated`, `unchanged` et `conflicts` correspondent au commit effectif. |
| `GET /fs/attrs` ; `POST /content/set_tags`, `/fs/attrs/set_tags`, `/content/batch_set_tags` | Tags `k=v`, dernière valeur d’une clé, `replace/append/clear`. Patch récursif atomique par cible ; le batch déduplique les URI canoniques (max. 50) et donne `{items, failed}`. Aucune projection mémoire implicite. |
| `POST /content/ensure_directory_index` | Conserve les sidecars existants et indexe les niveaux manquants. Écrit `fallback_abstract` **uniquement si les deux sidecars sont absents**. `created_abstract`, `indexed_levels` et `vector_status:complete` décrivent l’état réellement lisible. |
| `POST /content/reindex` | Reconstruit les vecteurs manquants ou tous avec `force:true`, à l’échelle du fichier/dossier (`recursive`), sans changer le texte source. Tags optionnels sur la cible. Les utilisateurs standards ne réindexent que leur namespace `user` propre. Avec le binding de génération et `semantic_and_vectors` sur un fichier de ressource non vide admissible, régénère les deux niveaux et réindexe le fichier dans un commit ; les dossiers ne sont pas régénérés. `mode:"full"` reste refusé. |
| `POST /search/{find,search}` ; `POST /search/{grep,glob}` | Sémantique texte et requêtes de métadonnées en liste ; voir ci-dessous. `grep` borné aux littéraux, ponctuation échappée, `. ^ $` ; `glob` prend `*`, `?` et `**`. Ces deux opérations ne demandent aucun embedding. |

URI NFC à casse significative, décodées une seule fois ; 20 segments, 160 octets par segment, 1 024 octets par URI. Segments `.`/`..`, séparateurs encodés, URI non Viking et identifiants de vecteurs bruts refusés. Les champs ACL intégrés à `mkdir`, `write`, `batch-write` et à l’import s’appliquent seulement à la cible autorisée (`manage`), sans modifier les parents créés automatiquement. Les variantes `use_snapshot` et `resolve_conflicts` ne sont pas portées ici ; les routes Archives sont un autre lot.

### Écritures et import `wait:false`

- **Batch write (`content_batch_write`).** Avec `wait:false`, l’acceptation en SQLite fixe en une transaction la tâche, les réservations sur les URI concernées et les nouveaux textes/tags/ACL, sans l’ancien index. Le reçu rend `created/updated/unchanged`, `task_id` et `vector_status:"queued"`. Le job vectorise les révisions réservées, revérifie ses droits, écrit tous les vecteurs et marque la tâche `completed` dans le même commit. Sur annulation, révocation ou erreur après acceptation, aucun nouvel index partiel n’est publié et les textes déjà acceptés restent lisibles selon leur ACL courante ; réindexer ou écrire à nouveau après résolution. `defer_processing:true` n’ouvre aucune tâche.
- **Import local stagé (`add_resource`).** Avec `wait:false`, le résultat `{status:"accepted",task_id,root_uri}` réserve le chemin effectivement alloué et le token de l’acteur. Aucun dossier ni texte importé avant le commit. Le job rejoue la route `wait:true` avec son identité fraîche et une réservation correspondant exactement au plan original. Publication du fichier, éventuels parents, ACL, vecteurs, consommation du token et fin du job sont atomiques. Seul cet import pose le marqueur interne `staged_atomic` qui autorise l’annulation pendant l’indexation ; la requête cliente ne peut pas le définir. Une tâche terminale qui n’a pas publié laisse le token réutilisable manuellement jusqu’à son expiration, sans reprise implicite du traitement ; un token d’un autre acteur donne toujours 404.
- **Attente et concurrence.** `POST /system/wait` du parent attend les tâches de la même identité et rend 504 à échéance si elles restent actives ; `GET /tasks/{id}` indique succès, annulation ou échec. Un projet voisin, un autre fichier, ou une opération après état terminal n’obtient pas un `409` artificiel. Un conflit de réservation exact/chevauchant est `409 RESOURCE_BUSY` tant que la tâche est réellement active. Sans queue, une demande asynchrone avec travail à faire répond 503 ; autrement les appels locaux sans `wait:false`, les écritures unitaires, skills, `ensure_directory_index` et `reindex` restent synchrones.

### Recherche et provenance

Le filtre utilisateur et les raccourcis `context_type`, `tags`, `since`, `until`, `time_field`, `level`, `target_uri` se cumulent avec les droits courants. L’DSL accepte prédicats d’égalité, `and/or`, `must/must_not`, `prefix/contains`, `range/range_out` et `time_range`, sur `uri`, `context_type` (`type`), `level`, `category`, `search_tags` (`tags`), `created_at`, `updated_at` et `size`. URI : `para="-d=0"` pour l’égalité, `-d=-1` pour le sous-arbre, `-d=1..20` pour la profondeur exacte. Bornes de temps : dates, ISO et relatifs `s`, `m`, `h`, `d`, `w`. Les champs d’identité/ACL et les prédicats non portés sont refusés, jamais ignorés.

Le résultat `{memories,resources,skills,total}` sépare les catégories. La recherche sémantique retourne des hits L0/L1 vers les sidecars visibles ou L2 vers les fichiers ; `read_content` joint le texte autorisé. `include_provenance` ajoute requête, racines lisibles, hits retournés et statistiques du moteur local, sans étapes de raisonnement ou reclassement fabriquées. Avec filtre de métadonnées et requête vide, le résultat est trié par date, `score:0`, sans embedding ni provenance ; il ne remplace pas la recherche sémantique. Recherche image, mots-clés via `search_type` et assembly ne sont pas implémentés dans ce routeur.

**Recherche avec session.** `POST /search/search` en mode liste accepte `session_id` avec une requête non vide, via le hook du parent `sessionSearchContext(id)`. Lecture seule, sans auto-création, même triplet compte/utilisateur/agent ; session absente/étrangère : 404 avant toute vectorisation. Session présente mais vide : recherche ordinaire. Le texte récent (au plus quatre messages utilisateur, 1 024 unités UTF-16) donne un contexte à un second embedding ; la combinaison normalisée conserve 65 % du vecteur de la requête et 35 % du vecteur contextualisé. Aucun texte de session n’apparaît dans le résultat/provenance, et les scopes/ACL de fichiers ne changent pas. Relecture après l’attente : une suppression donne 404 et une modification du contexte consommé donne 409. Ce n’est pas le plan d’intention multi-requêtes amont ; les identités déléguées sans le hook ne disposent pas de ce mode.

Chaque texte non blanc est vectorisé en blocs de 1 024 unités UTF-16 maximum. Le score est le meilleur cosinus de ses blocs (seuil par défaut `0.1`). Après un fournisseur asynchrone, la transaction revérifie identité, ACL et révisions avant publication. `503` si le fournisseur ou la forme des vecteurs est indisponible ; `429` si le budget est épuisé. **Aucun repli lexical.** Les textes blancs n’ont pas de vecteur. Les dimensions incompatibles ne coexistent pas ; un changement de modèle à dimension égale exige un `reindex` forcé cohérent des données concernées.

### Import et limites

1. `POST /resources/temp_upload` : un seul `file` multipart. `{temp_file_id,filename,size}` dans `result` ; zone temporaire liée au triplet compte/utilisateur/agent, expiration 30 min.
2. `POST /resources` : `{temp_file_id,source_name?,parent? | to?,create_parent?,reason?,tags?,tag_mode?,processing_mode?,acl?}`. `parent` réserve le premier nom libre (`_n` en cas de collision). `to` exact désigne un fichier textuel ou un dossier à créer ; pas de remplacement implicite. Cible par défaut `viking://resources`, ou `viking://~/resources` pour l’import privé.
3. Le token est consommé **dans** le commit fichier/index. En cas d’échec avant le commit, on peut reprendre avec le même token valide. Avec le hook `convertDocument` opt-in du parent, PDF/DOCX/XLSX/PPTX/PNG/JPEG admis peuvent être convertis ; seule la sortie Markdown (et le nom d’origine comme alias temporaire) est écrite, aucun binaire original. Un `source_name` correspondant exactement au nom choisi dans le sélecteur est remplacé par le nom `.md` de conversion. Les octets ne désignent pas de cible ni de fournisseur.
4. Un `path` URL HTTP(S) exclusif d’un token est transmis **uniquement** à `ctx.registerWatch`, sur destination texte explicite autorisée. Le parent filtre l’URL et possède la lecture, le job et le planning. Aucun accès URL arbitraire, connecteur, chemin local, archive/ZIP, HTML/SVG actif, ni jeton signé géré par Filesystem.

**Analyse du dossier nouvellement importé.** Pour `semantic_and_vectors`, un `to` de type dossier, un document stagé non vide/non caché et un `ctx.generate` opt-in, l’import prépare le L1 auprès du fournisseur (entrée bornée à 6 000 unités UTF-16, texte traité comme données ; protocole `openviking_edge_directory_summary_v1`, réponse JSON contenant uniquement `overview`). Le L0 est extrait de l’introduction du L1, pas recopié depuis le texte L2 : c’est le contrat de `semantic_processor.py::_extract_abstract_from_overview` au pin. Les deux niveaux ont leurs propres vecteurs et sont validés puis publiés atomiquement avec le document. Une erreur réelle de génération laisse le token et ne publie rien. Sans génération opt-in ou en `vectors_only`, les résumés non produits restent absents (`404`), jamais substitués par un titre ou un message d’attente.

**Import synchrone de document sans `to`.** Un fichier de ressource admissible, non caché et non vide, importé avec `wait:true` en `semantic_and_vectors` produit aussi cette paire quand le binding est activé. La racine `root_uri` reste le même fichier, dans le même montage ; ni nouveau dossier ni sidecar partagé n’est créé. Les deux niveaux ont leurs vecteurs, comptent dans les quotas et sont publiés avec le L2 et le retrait du jeton dans la même transaction. Un `level:[0,1]` explicite les retrouve sous l’URI du fichier ; sans sélection explicite, le classement ne gagne pas de doublons. `/content/read`, `stat` et `ls` gardent leur représentation de fichier. Ce nouveau chemin n’élargit pas l’analyse aux imports plats asynchrones ni aux destinations fichier explicites.

Chaque niveau généré est lié au **contenu** de son fichier source. Une lecture exige les ACL courantes du dossier, du niveau (pour un sidecar) et du fichier ; les vues/recherches omettent un niveau non lisible. Remplacer/supprimer la source invalide ses niveaux ; modifier simplement ses tags ou ses permissions ne réécrit pas les octets. Aucun calcul ni réparation sur GET. Les niveaux générés ne sont pas transportés par copie/déplacement/snapshot/pack et ne sont pas ajoutables à la suite d’un texte auteur par `append`. Les sidecars écrits explicitement restent des fichiers auteur. L’analyse récursive de dossiers existants reste hors de ce chemin.

Plafonds : 64 Kio UTF-8 par fichier, enveloppe multipart ≤ 8 Kio, entrée binaire ≤ 1 Mio si conversion active, résultat Markdown ≤ 64 Kio. Compte : 1 500 entrées, 16 Mio texte et 24 Mio vecteurs ; monte privée agrégée utilisateur et ses agents : 400 entrées, 4 Mio texte et 6 Mio vecteurs. Zone temporaire : 16 entrées par triplet, 32/1 Mio par utilisateur et 128/4 Mio par compte. Batch write : 64 opérations, 1 Mio JSON, 256 Kio de texte final. Reindex : au plus 256 fichiers à recalculer et 2 Mio de texte par opération. Listing 1 000, recherche sémantique 50, `grep/glob` 256 résultats ; `grep` lit au plus 2 Mio de données autorisées. Les quotas de la liaison IA peuvent resserrer les opérations ; aucune dérogation par plan ou changement d’agent.

### Skills inertes

`GET/POST /skills`, `POST /skills/validate`, `GET/PUT/DELETE /skills/{name}`, `POST /skills/find`, et `GET /skills/{name}/audit`. Entrées : `SKILL.md` UTF-8 complet, données structurées/MCP converties en Markdown inerte, ou un fichier textuel stagé. Frontmatter borné (valeurs simples, listes, mappings et texte bloc ; pas de tags, alias ni exécution YAML). `data.files` peut fournir des pièces jointes textuelles. Un `PUT` conserve le nom et remplace atomiquement le package avec les indexes ; la recherche groupe les hits par package avant la limite. Les manifests ont des SHA-256 ; l’auteur, l’horodatage, les révisions et l’audit de suppression sont déterminés côté serveur. Les métadonnées de provenance reçues ne font pas autorité sur l’identité. 48 nœuds de manifest et 256 Kio de texte par package ; 512 historiques distincts, 8 192 événements create/update par compte avant refus de nouvelles publications (la suppression peut toujours être journalisée).

Les répertoires Git, ZIP, refresh de source et les mutations de configuration de confidentialité ne sont pas effectués par cette API. Aucun texte ni fichier joint n’est activé ou exécuté. `GET /skills?target_uri=viking://system/compile/example-skills` et les lectures de `SKILL.md` sur cette monte utilisent le **même catalogue lecture seule** que Compile. Pas d’index sémantique inventé pour ces exemples.

**Fichier local dans le CLI stock.** Le CLI lit les octets chez le client, les téléverse en multipart `application/octet-stream`, puis envoie `{temp_file_id,list_only:true}` pour obtenir `{skills:[{name,description,path}],total}`. `path` n’est que le basename normalisé ; cette lecture ne crée ni skill ni vecteur et ne consomme pas le jeton. Le CLI stock téléverse ensuite de nouveau pour son POST d’installation ; un autre client peut réutiliser le même jeton de prévisualisation jusqu’au succès ou à l’expiration. Les deux requêtes exigent le même acteur (compte/utilisateur/agent), sinon `404`. Edge ne résout ni chemin client ni chemin hôte et ne conserve pas les chemins déclarés dans `source_metadata` d’un upload ; provenance serveur limitée au basename et mode local. Un jeton validé est revérifié et consommé dans la même transaction que le package, les vecteurs et le journal. Une erreur de validation ou d’indexation laisse le jeton intact, sans package partiel.

## Façade interne pour Archives, Compile et WebDAV

Importer de `src/filesystem.ts` ; aucune requête SQL brute nécessaire pour les données FS.

- `new Filesystem(ctx)` ; `path(uri).uri` pour la canonique, `check(uri, action)` pour la politique actuelle, `checkWriteParent(uri)` pour créer sous un parent existant (racines virtuelles autorisées si l’ACL le permet). `entry(path)` renvoie `undefined` pour une cible absente dont la politique autorise la lecture ; il ne répond **jamais** à la question « pouvait-on lire cette ancienne version ? ».
- `stat`, `read`, `list(uri, recursive=false)` (filtrage des enfants illisibles, pas de lecture stricte), `createDirectory`, `putText(uri,text,{mode?,expectedRevision?})`, `copyMove(from,to,{copy,recursive?,overwrite?})`, `deleteUri`.
- `captureSubtree(fs, uri, {allowMissing?,includeContent?,maxEntries?,maxBytes?})` est synchrone et strict : chaque entrée doit être lisible avant de lire le texte. Modèle v1, rev opaque triée, URI canonique, métadonnées, texte optionnel, politique directe et garde historique interne. `subtreeRevision` est une lecture stricte du token courant ou `null`. Ne pas présenter `guard` ou `entries[].acl` d’une capture à un lecteur ou dans un pack portable.
- `authorizeHistoricalRead(fs, capture)` est réservé aux captures du stockage de confiance. Même compte et même monte, politique capturée **et** ACL actuelle sur la même incarnation. S’il ne reste plus cette incarnation à l’URI partagée, seul l’admin de ce compte peut encore lire ; on ne déduit rien de l’ACL du parent. Un historique privé reste lié à sa monte même si la cible est supprimée.
- `validateSubtreeMutation(fs,uri,plan)` vérifie forme, révision et droits sans provider ni écritures. `prepareSubtreeMutation` fait la même validation avant d’embarquer les vecteurs. Plan `{expectedRevision:string|null, entries:[{path,is_dir,content?,description,tags,acl?}], delete?:string[], replace?:boolean}` : chemins relatifs, `''` pour racine ; `null` signifie absente. `replace` supprime les entrées non listées ; `delete` permet le retrait suivi d’une réécriture dans la même transaction. Les écritures ACL explicites exigent `manage`. Les mutations de montes gérées sont refusées.
- `commitSubtreeMutation(fs, préparé, callback?)` et `commitSubtreeMutations(fs, préparés, callback?)` revérifient CAS/ACL au commit ; jusqu’à 16 plans disjoints avec le **même** objet `Filesystem`. Callback **synchrone** dans la transaction pour journal/commit ; une erreur annule tout. `restoreSubtree(fs, uri, capture, expectedRevision)` restaure au même URI après autorisation historique, sans exposer d’endpoint supplémentaire. 256 entrées/2 Mio par mutation ; capture jusqu’à 512 entrées sur demande (2 Mio maximum). Le résultat est `{uri,revision,restored_count}` avec révision `null` si la cible a été supprimée.

## Preuve au SHA amont épinglé

```sh
npm run check
node --test tests/filesystem.test.mjs
```

**51/51 tests et sous-tests** dans le lot filesystem local (Node 26.10.0, Miniflare / workerd et SQLite réels, espaces jetables), et TypeScript vert. Embeddings, conversion et génération sont des fixtures explicites, sans appel Workers AI réel ni sortie réseau. Le Worker parent est réellement monté pour les preuves de file/attente, de parcours Studio et d’indisponibilité du fournisseur ; le DO fixture contrôle notamment tags, sidecars, ACL de destination et historique, rollback journal/restore, conversion et skills.

**Correctif PAR-01 (audit indépendant).** `node --test --test-name-pattern='PAR-01' tests/filesystem.test.mjs` : **1/5 avant** (les quatre refus attendus renvoyaient 200), **5/5 après**. Suppression récursive, déplacement, copie avec écrasement et déplacement avec écrasement : refus 403 sans variation de révision, de listing, d’ACL ni de résultats d’index ; chaque opération aboutit après octroi explicite de `manage`. Le remplacement de fichier en place avec `write` reste valide sans changer son ACL. Les tests passent par REST et le stockage commun ; ils n’attestent pas à eux seuls les adaptateurs WebDAV ou MCP.

**Sept cas HTTP d’origine verts, assertions non réécrites.** Dans `tests/fs/original-contract.py`, les fichiers au SHA sont vérifiés par SHA-256 et lus exclusivement comme données : interprétation d’un sous-ensemble d’AST (pas d’import/exécution du module Python amont ni d’exécution des skills).
