# MCP natif sur Workerd — couverture et limites

Référence OpenViking : `000f0765d7ec183886fbabbc22e69bc289cc429d`, copie `upstream/` en lecture seule. Les contrats de `server/mcp_endpoint.py`, `server/routers/{mcps,user_settings,openviking_assets}.py` et des services associés ont été lus comme des données, sans exécuter le code amont. Le filtre a signalé des extraits descriptifs contenant des exemples de transfert ; aucune de ces instructions n’a été suivie.

## Montage et activation

Le Worker parent laisse passer `/mcp` et `/mcp/` dans son filtre de routes, sous la même authentification par clé (`X-API-Key` ou `Authorization: Bearer`) et le même contrôle d’origine que les routes de données. Le Durable Object du compte appelle `initMcp(ctx)` dans son initialisation SQL, puis `routeMcp(request, url, ctx)` avec l’identité déjà résolue et les ACL du workspace. `isMcpHttpPath()` identifie uniquement ces deux chemins. Le parent garde son enveloppe HTTP pour les erreurs d’authentification avant dispatch ; après admission, le transport MCP répond en JSON-RPC.

| `OPENVIKING_EDGE_MCP` (variable opérateur) | Effet |
|---|---|
| Absente ou différente des deux valeurs reconnues | `/mcp` et `/api/v1/mcps` fermés, `503` pour un appelant authentifié |
| `read` | Outils de lecture et consultation/validation du registre ; pas de mutation MCP/registre |
| `read-write` | Outils de lecture et mutations explicites du stockage ; gestion du registre selon le rôle |

La variable est lue côté serveur (`WorkspaceContext.mcpMode`), jamais depuis le client. Ce module ne modifie pas les scopes OAuth du parent : les jetons OAuth délégués ne donnent pas accès à ces routes. Les deux familles REST annexes (résolution de manifestes et préférences) restent authentifiées même quand MCP est désactivé.

## Surface portée

- **`POST /mcp`** — Streamable HTTP sans état serveur : `initialize`, `ping`, `tools/list`, `tools/call`. Négociation `2025-11-25`, `2025-06-18` ou `2025-03-26`, réponse JSON ou un événement SSE suivi de la fermeture. Pas de session, de reprise, de stream `GET`, ni de batch JSON-RPC. Une notification sans identifiant ne déclenche jamais d’outil. Les erreurs d’opération sont des résultats `isError`, pas des mutations annoncées comme réussies.
- **Lecture** — `read`, `list`, `tree`, `find`, `search`, `grep`, `glob`, `health`, `list_users`, `list_groups`, `get_acl`. Le texte est lu tel qu’il est stocké, sans évaluation d’un nœud. L’annuaire ne divulgue ni clés ni adhésions aux groupes. `find`/`search` emploient la recherche du filesystem et son budget d’embeddings ; pas de repli lexical pour une requête sémantique, ni d’assemblage de contexte de session. `read` est limité à quatre URI et échoue entièrement si une lecture échoue. `grep` admet jusqu’à quatre motifs dans le sous-ensemble borné du filesystem ; les résultats textuels MCP sont plafonnés à 256 Kio avant enveloppe.
- **Écriture explicite** — `write`, `edit`, `forget`, `set_acl`, `add_resource`, `add_skill`. Les opérations sont transmises, en mémoire et sans en-têtes de clé, aux routes fixes de `routeFilesystem` ; pas d’autre chemin de données. `edit` vérifie la révision du contenu au commit via le garde de la transaction d’écriture. `create` refuse un fichier existant, `append` exige un fichier existant : c’est le contrat du filesystem edge, pas les alias de l’amont. Par prudence, `forget` récursif dans les ressources partagées est réservé aux admins du compte (PAR-01). `add_resource` consomme un `temp_file_id` créé par `/api/v1/resources/temp_upload` pour la même identité ; `add_skill` prend seulement le texte explicite de `SKILL.md` et ne l’exécute pas.
- **`/api/v1/mcps`** — enregistrement, liste, détail, statut, validation, synchronisation, recherche sémantique du catalogue et invocation nommée. Seule adresse admise : `viking://builtin/openviking-data`, un identifiant interne sans URL réseau ni en-têtes. Le catalogue contient huit outils locaux de lecture (`health`, `list`, `tree`, `read`, `find`, `search`, `grep`, `glob`). Les révisions sont persistées et vérifiées avant invocation ; `/status` mesure uniquement si le catalogue local est à jour. Les URI de catalogue sont des identifiants de registre, pas des fichiers ni des nœuds exécutables. Portée privée `viking://~/tools`, ou partagée au sein du compte `viking://agent/tools` (gestion admin, lecture membre). Quotas : huit enregistrements par portée et 32 par compte. Aucune adresse externe, aucun en-tête d’authentification et aucune définition d’outil client ne sont stockés.
- **`GET/PATCH/DELETE /api/v1/user-settings/add-locations`** — préférences utilisateur (`resource_uri`, `skill_uri`), persistées par compte et utilisateur. PATCH sparse ; `null` retire une valeur, DELETE retire les deux. Destination ressources : dossier existant, autorisé en écriture. Destination skills : racine privée ou racine partagée pour un admin. Les outils `add_resource` et `add_skill` les utilisent sans cible explicite et revalident leurs droits à l’opération. Sans préférence, ces outils choisissent l’espace privé. Ces préférences ne changent pas les appels directs REST d’import ; pas de défaut de déploiement hérité.
- **`POST /api/v1/openviking-assets/resolve`** — plan en mémoire, sans accès à Git : manifeste plat en JSON ou YAML borné (maps/listes en blocs, scalaires simples, listes scalaires entre crochets), catalogue inline ou séparé, sélection, défauts, destinations Viking normalisées, refs et IDs de source déterministes. Pas d’inclusion, d’alias YAML, de tags personnalisés ou de lecture de fichiers. Maximum 128 Kio de texte par document, 128 entrées par catalogue. Le résultat n’atteste ni la connectivité ni la possibilité de publier. **`POST /preflight` répond `501`** avant lecture de l’authentification du dépôt : aucun connecteur Git approuvé n’est monté.

Hors portée : services MCP externes, `mount`/`batch-mount`/démontage et Live Context exécuté, commandes, URLs d’import, téléchargements signés, média MCP, watches, écriture de souvenirs par modèle et génération. Rien ne lance un outil à partir d’une réponse de modèle ou d’un résultat de lecture. Le parent peut utiliser son binding d’embeddings configuré pour la recherche et l’indexation ordinaires ; aucun autre client ou binding externe n’est appelé par ce module.

## Vérification locale

`node --test --test-concurrency=1 tests/mcp.test.mjs` : **12/12** (10 scénarios racine et deux sous-tests de redémarrage), sur le point d’entrée parent et de vrais Durable Objects SQLite, Node 26.10.0 / Miniflare 5.20261119.0-beta / Workerd 1.20261119.1. Le harnais refuse les sorties HTTP, désactive la télémétrie du runtime de test et emploie uniquement des clés et données synthétiques. Le binding d’embeddings est une fixture locale ou absent selon le cas. `npm run check` : vert.

Preuves : négociation JSON/SSE et contrôle d’origine, lecture littérale/ACL, mutations explicites, cloisonnements inter-utilisateur et inter-compte, échec sans embeddings, registre et préférences relus après réouverture de SQLite, imports textuel et skill, résolution de manifeste sans effet externe et refus du préflight. Ni suite MCP Python d’origine, ni fournisseur réel, ni Cloudflare distant n’ont été exécutés : pas d’affirmation de parité intégrale ou de validation de production.

Rejeu conjoint `node --test --test-concurrency=1 tests/mcp.test.mjs tests/filesystem.test.mjs tests/worker.test.mjs` : **52/52** (zéro échec ou skip) sur l’intégration finale locale. La première passe donnait 48/52, dont quatre échecs `PAR-01` dans les tests REST du filesystem général ; les quatre sont verts après le correctif concurrent du filesystem, hors de ce lot. Le garde MCP de suppression récursive partagée reste vérifié et conservé.
