# Parité OpenViking → Cloudflare Workers

Référence : `volcengine/OpenViking@000f0765d7ec183886fbabbc22e69bc289cc429d`. Version locale `0.1.0-alpha.1`. **Port natif en cours de qualification, non déployé.** La matrice n’attribue pas une parité complète aux fonctions décrites comme partielles ou dépendantes d’un fournisseur de test.

## Architecture et limite du port direct

L’amont assemble un serveur FastAPI/Uvicorn, ses backends de stockage et des extensions natives. `pyproject.toml` déclare notamment la distribution de `ragfs_python*.so` et du moteur `vectordb/engine/*.abi3.so`, et installe des dépendances de parsing, d’authentification, de modèles et d’observabilité. Un Worker n’est pas un processus Linux capable de charger ces extensions ou de démarrer Uvicorn sur un port. L’existence de Python et de WASM sur Workers ne suffit donc pas à y exécuter la distribution telle quelle. Le port maintient un contrat HTTP compatible sur les routes réellement adaptées, sur un runtime Worker TypeScript natif. Un conteneur Python devant un Worker préserverait plus facilement les tests backend Linux, mais ne démontrerait pas le port natif demandé.

Les requêtes privées sont authentifiées avant routage vers un Durable Object par compte. Les DO de contrôle et d’OAuth sont distincts du plan de données. Les modules utilisent SQL préparé, transactions synchrones et alarmes persistées. Aucune bascule vers un processus ou serveur OpenViking. Les rares intégrations sortantes sont optionnelles, bornées et autorisées côté opérateur, pas par un modèle ou une URL arbitraire. La déclaration des bindings Cloudflare ne prouve pas leur fonctionnement distant.

`python3 scripts/inventory-upstream.py` : **247 déclarations de routes** par décorateurs dans `openviking/server` et `openviking_gateway` (247 chemins statiquement résolus, hors préfixes de montage et assemblages dynamiques). C’est un inventaire de travail, pas un chiffre de couverture, plusieurs variantes/profils pouvant partager des chemins.

## Preuves à ne pas confondre

1. **Référence Linux** : [rapport final des tests originaux](../.work/original/RESULTATS.md). Les quatre modules du profil Lite passent (**107/107**) ainsi que les contrats HTTP ASGI hors ligne (**17/17**). Quatre échecs restent dans le lot core (308 réussites) ; les quatre échecs initiaux du lot domaine ont été levés dans le module filesystem rejoué avec sa configuration. La référence Linux ne valide pas le Worker et ne constitue pas une recette exhaustive de l’amont.
2. **Rejeu HTTP d’origine** : voir [la campagne stricte](ORIGINAL-REPLAY.md), qui sépare chaque instance, garde les vrais rouges et refuse les tests verts qui acceptent une réponse hors contrat. Assertion et fichier upstream inchangés ; la fixture de transport pointe vers le vrai Workerd local. Des sous-suites d’origine supplémentaires sont rattachées à [la preuve filesystem](FILESYSTEM.md) ; ne pas additionner les chevauchements.
3. **Tests du port** : `npm run check`, `npm test`, scénarios SQLite Durable Objects dans Workerd local. Les fixtures AI/texte vivent dans le harnais, pas dans le bundle d’empaquetage. `python3 scripts/receipt.py` calcule les empreintes de la source/config/tests et de l’entrée HTML ; les lancements locaux journalisent aussi le SHA du JS réellement servi par le harnais.
4. **Web Studio** : vraie compilation avec prébuild Node 22. Le [rapport Studio](STUDIO.md) et [les cohortes](../.work/studio/COHORTES.md) distinguent l’exécution de tous les fichiers de la réussite de tous les tests. Le blocage de fermeture Vitest a été diagnostiqué et corrigé dans le harnais isolé.
5. **Navigateur réel** : [audit initial](UX-REVIEW.md), [contre-relecture](UX-PARITY.md). Recherche et ouverture du document fictif vérifiées, ainsi que [VikingBot](vikingbot-workers-local.png) sur le vrai Workerd avec AI de test (HTTP SSE 200, aucun modèle distant). Les audits indiquent le SHA de chaque interface testée et les réserves restantes.
6. **Cloudflare distant** : `wrangler deploy --dry-run` vérifie seulement l’empaquetage des bindings SQLite, AI et Assets, sans publication. DNS, compte, WAF/Access, disponibilité des modèles et charge de production non vérifiés. [Relecture sécurité](SECURITY-PARITY.md) distincte. Des extraits amont signalés heuristiquement ont été traités comme des données ; les validations d’origine ont été isolées.

## Suite nécessaire avant de déclarer « complet »

1. Conserver les échecs de compatibilité et couvrir chaque famille manquante par comportement mesurable contre la référence. Définir un format d’export/import supporté avant de migrer des données réelles.
2. Porter le contexte hiérarchique et la récupération avancée, les workflows d’ingestion et de mémoire, puis l’administration, les ACL et les autorisations originales. Définir les limites de ressources et la stratégie de reprise sur panne par domaine.
3. Porter et tester séparément les services qui dépendent aujourd’hui de processus, du réseau ou d’extensions natives. Considérer Workers AI/Queues/R2/Vectorize ou WebAssembly par sous-système ; ne pas substituer un proxy sans nouveau cadrage explicite.
4. Exécuter les suites amont HTTP contre le Worker sans abaisser leurs assertions, établir les équivalents des tests internes natifs qui ne peuvent pas s’exécuter sous workerd, couvrir les parcours Studio et documenter les écarts qui restent. Après autorisation de déploiement seulement, confirmer les bindings et l’identité du build sur un environnement Cloudflare distinct avant toute exposition.
